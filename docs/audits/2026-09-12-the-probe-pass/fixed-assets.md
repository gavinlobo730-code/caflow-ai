## 2. Defects with no finding at all

1. **The Register tab shows soft-deleted assets, and its Gross Block includes them.** `apps/web/app/clients/[id]/fixed-assets/page.tsx:261-267` reads `fixed_assets` directly over PostgREST with `.eq("client_id", …).eq("is_disposed", false)` and **no `deleted_at` filter**, while every backend read excludes them (`routers/fixed_assets.py:589` `list_assets`, `:355-360` `_live_asset`, `:967` the runner, `:1608` the schedule, `routers/year_end_notes.py:187`). The Delete dialog tells the CA "the asset leaves the register" (`page.tsx:577-580`); it does not. The tab's totals (`:295-297`) then disagree with the Depreciation tab, the year-end note and register-integrity by exactly the deleted asset's cost. One-line fix: `.is_("deleted_at", null)` on that select.
2. **A depreciation charge is refused once the client's GSTR-3B for that month is filed — the exact case CLAUDE.md names as the reason not to do this.** `routers/fixed_assets.py:804` calls `period_lock_service.assert_open`, which is `lock_reason` — the WHOLE rule including "a return covering the date has been filed" (`services/period_lock_service.py:93-97,280-293`, `reason_from_tables:250-275`). CLAUDE.md: *"a kernel refusal would stop every June receipt, payment, bank entry, **depreciation charge** and payroll accrual from the 11th onwards."* A practice that files June's 3B on 20 July and closes June's books on the 25th cannot post June depreciation at all, and a filed return is the one refusal a CA cannot undo in-app. **This is deliberate and test-pinned** — the router comment at `:798-803` says so, and `apps/api/tests/test_a_year_of_depreciation_is_one_request.py:158-168` `test_a_locked_period_stops_that_asset_and_says_why` seeds `lock_reason = "GSTR-3B for April 2026 was filed on 18-05-2026."` So it is an **owner decision to re-take**, not a bug to quietly swap for `closure_reason`; doing that silently breaks a green test.
3. **The mirror of (2): asset CREATION with claimable ITC is not lock-checked at all.** `routers/fixed_assets.py:637` calls only `period_validation_service.validate_posting_date` (firm-FY), and the acquisition journal can post a `%GST Input%` debit (`phase2_journal_service.py:1331-1338`) — a figure that feeds GSTR-3B Table 4(A). Meanwhile `correct_asset:1249` and `delete_asset:1426` **do** call `assert_open` on the same date. So a CA can create a June asset with June ITC after June's 3B is filed, but cannot then correct it. `dispose_asset:1066` is likewise closure-only.
4. **`FA-DEPN-` references disagree between the writer and the reverser for an asset whose `asset_code` is NULL.** `phase2_journal_service.py:1439` builds `f"FA-DEPN-{asset.get('asset_code', asset['id'][:8])}-{period}"` — `dict.get` with a default only substitutes when the **key is absent**, not when the value is `None` — while `routers/fixed_assets.py:1509` and `:1537` build the lookup with `asset.get('asset_code') or asset['id'][:8]`. For a row with `asset_code IS NULL` the journal is written as `FA-DEPN-None-2026-04` and `POST /{id}/depreciation/{period}/reverse` 404s ("No live depreciation journal found"). Worse, `FA-DEPN-None-{period}` is the **same reference for every code-less asset of that client in that month**, and `_create_journal` dedupes on `(client_id, reference_no, entry_date)` — so the second one's charge never reaches the GL while its register row moves. Same pattern at `:1352` (`FA-CAP-`), `:1393` (`FA-ACQ-`), `:1527` (`FA-DISP-`). Reachability is bounded: the only insert path (`routers/fixed_assets.py:682`) always sets a code, and migration 351's unique index is `WHERE asset_code IS NOT NULL`, so NULLs can only be legacy rows created between migrations 025 and 054 — I could not measure whether any exist. Fix is one character class: `.get('asset_code') or …` in all four.
5. **The disposal's own honesty field is not rendered.** `routers/fixed_assets.py:1131-1141,1156` computes and returns `part_month_depreciation_not_charged` precisely so the CA is told the gain is a part-month short; `grep -rn 'part_month' apps/web` returns nothing.
