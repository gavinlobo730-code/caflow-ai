# Edge protection: security headers and per-address limits

> **THE CLOUDFLARE HALF OF THIS DOCUMENT IS NOT APPLIED.** No rule below has been created, previewed or
> tested in the Cloudflare account, and no Supabase setting named here has been read or changed. What IS in
> the repository and ships with the next deploy: the security headers on both sites and the API, and the
> in-process per-address limits on the routes that need no login. Everything under "What only a person can
> do" is a proposal for the owner to ratify, with the thresholds and expressions written out so it is a
> twenty-minute job and not a design task. Facts about Cloudflare's own limits were read from its
> documentation on 02-10-2026 (IST) and its documentation moves; read the plan page before relying on a number.

Two audit items, one document: `security_privacy-05` (no security headers anywhere) and `ops-30` (no limits at
the edge, one single worker that a noisy caller can exhaust).

## 1. What the code does now

### 1.1 Headers

| Surface | What sends it | Headers |
|---|---|---|
| Product site (`caflow-ai.pages.dev`) | `out/_headers`, generated by `apps/web/scripts/security-headers.mjs` after `next build` | `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` |
| Marketing site (`practicesync.pages.dev`) | `out/_headers`, generated by `apps/marketing/scripts/security-headers.mjs` | the same six, with a narrower CSP |
| API (`practicesync-api.onrender.com`) | `middleware/security_headers.py` (pure ASGI, outside CORS) | `X-Content-Type-Options: nosniff` on every response; `Cache-Control: no-store` on JSON (never over a route's own); `Strict-Transport-Security` only when `APP_ENV=production` and the request was secure |

Decisions worth knowing before changing any of it:

* **The CSP's `connect-src` names three hosts exactly** (the API, Supabase, the error tracker if a DSN is
  built in) and never a wildcard, because a wildcard on `*.onrender.com` or `*.supabase.co` lets anyone who can
  create a service there receive what a script stole. That directive is the main mitigation for the Supabase
  session living in `localStorage`. The three are read at build time from the same `NEXT_PUBLIC_*` values the
  bundle was built with, so they cannot drift from what the app actually calls.
* **`script-src` has `'unsafe-inline'`**, because a Next static export puts its bootstrap in inline scripts and
  `_headers` cannot carry per-page hashes (100 rules, 2,000 characters a line). There is no `'unsafe-eval'`.
* **HSTS is 30 days, with no `includeSubDomains` and no `preload`.** A browser told HSTS cannot be told
  otherwise until it expires. Raising it is one constant in each of three places, held equal by
  `apps/api/tests/test_the_two_sites_send_the_same_security_posture.py`.
* **The way back for the CSP needs no code change.** Set the Cloudflare Pages build variable
  `SECURITY_CSP_MODE` to `report-only` (the browser console says what would have been blocked, nothing is) or
  `off`, then retry the deployment: a static export has no runtime, so the rebuild is the switch. The other
  five headers are not affected by it. There is no report endpoint, so report-only is for a person with
  DevTools open.
* `Cache-Control` is not touched on either site: Pages' own `public, max-age=0, must-revalidate` is right.

### 1.2 Per-address limits (the API)

`middleware/public_rate_limit.py`. A refusal is a 429 with `Retry-After`, in `{success, data, error}`, through
CORS so the page can read it. The key is `core/client_ip.client_ip` (the Nth entry from the right of
`X-Forwarded-For`, `TRUSTED_PROXY_HOPS`, default 1), never the first entry the caller typed.

| Bucket | Budget per address | Routes |
|---|---|---|
| `esign` | 120 / 60 s | the three engagement-letter routes (the limit is the router's, so a fourth is covered) |
| `invite` | 120 / 60 s | the three accept-invite routes (staff, client portal, employee) and the employee activation-session |
| `form` | 120 / 60 s | the demo-request router (its own three-per-quarter-hour cap stays inside the handler) |
| `signup` | 60 / 1 h | firm creation |

A signed-in member's requests are not behind any of these. Routes whose limit lives elsewhere are named, with
the module that holds it, in `tests/test_every_public_route_is_rate_limited.py`: the two signed webhooks (unsigned
requests are counted AFTER the signature check, so a flood can never lock the real sender out), the scheduler
trigger (counts wrong tokens only), `/health`, `/ready` and `/`.

**Why these numbers do not refuse a real CA.** The unit is an address, and an office is one address. 120 a
minute is two requests a second for a full minute: a prospect's signing page makes two requests in total, and
an employer who emails every employee an activation link and watches sixty of them click it from one office
makes about two each. A script is stopped inside a second. If `TRUSTED_PROXY_HOPS` were wrong and every caller
keyed to one proxy address, 120 a minute across the whole public surface is still far above what it carries.

**What it cannot do.** The windows are in this process: right for the one worker the service runs today, wrong
for several (each would allow the full budget) and forgotten on a restart. There is no shared store and none was
built. It does not stop a flood from many addresses. The body of a POST is read before a dependency runs, so a
caller sending large bodies costs that read (`middleware/body_limit.py` bounds it at 32 MB).

## 2. What was checked, and what was not

Checked on 02-10-2026 (IST), in the sandbox where the change was written:

* `curl -I` on `https://caflow-ai.pages.dev/login/` and `https://practicesync.pages.dev/` (the only hosts that
  sandbox can reach): Cloudflare already sends `referrer-policy: strict-origin-when-cross-origin`,
  `x-content-type-options: nosniff` and `access-control-allow-origin: *` by default, and sends no HSTS, no CSP,
  no `X-Frame-Options` and no `Permissions-Policy`. So the audit's "is some of this already added by Cloudflare"
  has an answer: two of the six, and the generated file states both explicitly so it does not depend on a
  default Cloudflare may change.
* (Why the default is report-only: see 3.1 step 4.) The product's built export was walked (170 screens) in Chromium with the generated policy ENFORCED:
  no screen threw, none logged a console error, none raised a `securitypolicyviolation` event. Breaking the
  policy on purpose (`connect-src 'none'`) turned the walk red in both enforce and report-only mode.
* The exact policy was exercised in Chromium against a page with a second and third origin: the API and
  Supabase origins were reachable, a third origin was refused (from the page and from the service worker), a
  `data:` image loaded, an `http:` image was refused, an inline script ran, the engagement letter's sandboxed
  `srcdoc` iframe rendered its own inline `<style>`, a CSV download worked, and a PDF opened from a `blob:` URL
  in a new tab still got the browser's PDF viewer under `object-src 'none'`.
* A real `uvicorn` on the real app, hit with `curl` from one address: 130 requests to
  `GET /api/public/demo-request/options` answered 120 × 200 then 429 with `Retry-After`, the envelope,
  `Access-Control-Allow-Origin`, `nosniff` and `no-store`; 130 to an engagement-letter route answered 120 × 404 (a
  one-character token matches no letter) then 429, and the sign and decline POSTs on the same router were refused
  from the same address; the demo form's own cap answered 429 with `Retry-After: 900` on the fourth submission; a
  signed-in request from the address that had spent its public budget still answered 200 (dev header-auth mode,
  and `test_every_public_route_is_rate_limited.py` holds it without a server).

**Not verified, and the list is part of the work:**

* That Cloudflare applies `_headers` to a response it serves through a `_redirects` rewrite. Every
  `/clients/<id>/…` page is one. Its documentation says a redirect takes priority over a header rule and is
  silent on a rewrite. If they are not applied there, those pages carry no CSP (nothing breaks) and
  `apps/web/scripts/check-live-headers.mjs` prints a warning naming the gap.
* The API's own headers on the deployed host: that host cannot be reached from the sandbox, and that Render
  forwards `X-Forwarded-Proto: https`, which is what makes HSTS appear.
* Firefox and Safari under the policy. Real Supabase, Render and Sentry hosts (the walk is same-origin by
  design; the semantics were proved on a synthetic page).
* The Pages build command in the dashboard. Both `build` and `pages:build` run the generator; a command that
  calls `next build` directly does not, and ships no headers without a word.

## 3. What only a person can do

### 3.1 After the deploy lands (about ten minutes)

1. Read the Pages build log for `security-headers: wrote out/_headers (CSP report-only; connect-src …)`. The origins
   listed must be the API and Supabase hosts, and no `could not derive` line may follow. If `NEXT_PUBLIC_SUPABASE_URL`
   was not a build variable, say so now: the policy would omit Supabase.
2. Run, and compare with section 1.1:

   ```
   curl -sI https://caflow-ai.pages.dev/login/
   curl -sI https://caflow-ai.pages.dev/clients/00000000-0000-4000-8000-000000000001/accounting/
   curl -sI https://practicesync.pages.dev/
   curl -sI https://practicesync-api.onrender.com/health
   ```

   The first and third must show all six headers. The second answers the open question above. The fourth must
   show `x-content-type-options: nosniff`, `cache-control: no-store` and `strict-transport-security: max-age=2592000`.
   `node apps/web/scripts/check-live-headers.mjs https://caflow-ai.pages.dev --marketing`
   does the first three and is wired into the scheduled `Live redirects` workflow.
3. Open the product in a browser with DevTools open on the Console and do the things the walk cannot: sign in
   (a real Supabase session), open a client, save something, export a spreadsheet, open an invoice PDF in a new
   tab, open an engagement-letter link, start MFA enrolment (the QR code is a `data:` image) and view the branding
   screen with a logo set. Any `Refused to …` line is a CSP violation.
4. **The policy is deployed as REPORT-ONLY and enforcing it is YOUR decision, made after step 3.** `SECURITY_CSP_MODE`
   defaults to `report-only` (the header is `Content-Security-Policy-Report-Only`): the browser's console names what the
   policy WOULD have refused and refuses nothing, and the other five headers are enforced either way. The policy was
   walked enforced across 170 screens in Chromium, but never against the real Supabase, Render and error-tracker
   hosts, Safari or Firefox, and a wrong ENFORCED policy stops sign-in for every user and says nothing, so the first
   deployment reports. In step 3 a violation reads `[Report Only] Refused to ...`.
   * **No such line after step 3 (and a pass in Safari and Firefox if you use them):** set
     `SECURITY_CSP_MODE=enforce` as a Pages build variable on the product project (and on the marketing project) and
     retry the deployment, then repeat step 3 once.
   * **Any such line:** do not enforce. Tell whoever maintains the generator which host or feature it named; the
     fix is in `apps/web/scripts/security-headers.mjs` (and its marketing sibling), then repeat step 3.
   * **To go back from enforce at any time:** set the variable to `report-only` (or `off`) and retry the deployment;
     no code change, and the other five headers do not move.
5. Check that Cloudflare Web Analytics is OFF for both projects. The policy has no entry for its beacon (an owner
   decision that the sites run no analytics), so if it is on the console will show it refused.

### 3.2 Edge rate limiting (NOT APPLIED)

**Precondition that does not hold today.** Cloudflare rules apply to hostnames in the owner's Cloudflare zone. The
API is `practicesync-api.onrender.com`, which is Render's, so no Cloudflare rule can see it, and the two Pages
hostnames are `pages.dev`, which are not in the owner's zone either. Every step below starts with a custom domain.

1. Add a custom domain for the API in Render (for example `api.<your-domain>`), and a proxied (orange cloud) DNS
   record for it in the Cloudflare zone.
2. **In the same change, set `TRUSTED_PROXY_HOPS` to 2** in the Render dashboard and verify it as the header of
   `core/client_ip.py` describes (send `X-Forwarded-For: 203.0.113.9` and read the address the signing event
   records beside it; `render.yaml` carries the same instruction). With Cloudflare in front the chain is the client,
   then Cloudflare, so one hop would key every limiter on a Cloudflare edge address and refuse real callers
   together. Do not turn the proxy on before this is done.
3. Point `NEXT_PUBLIC_API_URL` at the new hostname in **both** `apps/web/wrangler.toml` and the production
   fallback in `apps/web/next.config.mjs` (`scripts/api-url.test.ts` fails if they disagree), in
   `apps/marketing/wrangler.toml` and its `next.config.mjs`, and add the origin to `ALLOWED_ORIGINS` only if the web
   origins changed. The CSP follows the variable with no further edit.
4. **The origin is still reachable directly** at the Render hostname, which bypasses every Cloudflare rule, and with
   `TRUSTED_PROXY_HOPS=2` a caller who goes round Cloudflare can write the entry the limiter keys on. Render does not
   offer an origin that accepts only Cloudflare's addresses without a paid feature or a shared secret header. Until that
   is closed the edge rules reduce noise from honest scripts and do not stop a determined caller. Say so to whoever
   asks.
5. Create the rules (Security, WAF, Rate limiting rules). The edge budget is deliberately LOOSER than the in-process
   one, so a real user always meets the precise limit first and the edge only meets floods.

   **Free plan** (Cloudflare documents one rule, a 10-second counting period and a 10-second mitigation timeout):

   ```
   Name:        public and token routes
   Expression:  (http.host eq "api.<your-domain>" and (
                   starts_with(http.request.uri.path, "/api/public/") or
                   http.request.uri.path in {
                     "/api/identity/accept-invite"
                     "/api/portal/accept-invite"
                     "/api/portal/employee/accept-invite"
                     "/api/portal/employee/activation-session"}))
   Characteristic: IP
   Requests:    50 per 10 seconds   (five a second sustained; the in-process limit is two)
   Action:      Block, for 10 seconds
   ```

   **Pro plan and above** (two rules or more, periods up to a minute) add:

   ```
   Name:        demo request
   Expression:  (http.host eq "api.<your-domain>" and http.request.method eq "POST" and
                 http.request.uri.path eq "/api/public/demo-request")
   Characteristic: IP
   Requests:    5 per 60 seconds
   Action:      Block, for 10 minutes
   ```

   **Not recommended until measured:** an API-wide rule. An office behind one address legitimately sends hundreds of
   requests a minute across a dozen staff, and a figure written without the `caflow.access` log lines in front of
   you is how a practice gets locked out on a month-end morning.
6. Verify (replace the host; run it from one machine, in a minute that has not been used):

   ```
   for i in $(seq 1 130); do curl -s -o /dev/null -w "%{http_code}\n" https://api.<your-domain>/api/public/demo-request/options; done | sort | uniq -c
   for i in $(seq 1 130); do curl -s -o /dev/null -w "%{http_code}\n" https://api.<your-domain>/api/public/engagement-letters/x; done | sort | uniq -c
   ```

   Expect 120 of the first status and the rest 429 (from the app), and with the edge rule on, an earlier 429 only if
   the loop ran faster than fifty requests in ten seconds. While it runs, an authenticated call from the same
   machine (`curl -H "Authorization: Bearer $TOKEN" https://api.<your-domain>/api/identity/permissions`) must answer 200.

### 3.3 Sign-in, which is Supabase's and not this API's

Sign-in, sign-up and password reset go from the browser to the Supabase project, never through the API, so
neither the in-process limits nor a Cloudflare rule on the API hostname touches them. Their limits are the
project's own (Supabase dashboard, Authentication, rate limits), and whether to add a CAPTCHA there is a decision
for the owner. **Read the current values on that screen**; this document deliberately states none.

### 3.4 Not built, on purpose

* **A bot challenge on the demo form** (Cloudflare Turnstile or any CAPTCHA). It is a third-party script on the
  marketing site, against the owner's decision that the sites load nothing from another host, and it needs the CSP
  widened. The honeypot, the per-address caps and the edge rule above are what stand in for it.
* **A shared store for the windows.** One worker today; when that changes, the in-process limiters become N times
  looser and the edge rules above become the real limit.
* **An alert when a limiter refuses.** The log line is `caflow.public_rate_limit`, one a flood (the first ten, then
  every hundredth), naming the bucket and never a path or an address.
* **A report endpoint for CSP violations.** A violation report carries the page URL, which holds a client's id,
  and nothing here receives it. The error tracker's scrubber does not run on a browser's own report, so it was not
  pointed there.
