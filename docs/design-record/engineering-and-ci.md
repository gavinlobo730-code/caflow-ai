- **THE SMOKE WALK RUNS BY ITSELF, NIGHTLY AND ON DEMAND, AND IS NOT A CHECK ANYTHING WAITS ON** (engineering-15). `scripts/smoke-walk.mjs` fails on a crash, a console error, a blank body, an unexpected redirect or a herd of identical bodies, was run by hand only, and CLAUDE.md records thirteen screens crashing the first time it could render them. `.github/workflows/smoke-walk.yml` builds with `pnpm smoke:build`, adds `@playwright/test` at an exact version to THAT job only (`package.json` untouched, so the job every pull request runs pays nothing), and runs at 02:00 IST, on dispatch, and on a pull request only for the label `smoke-walk` (`types: [labeled]` plus a job `if`): **no `push`, no `paths:` filter, never a required check.** `--report` writes the verdict as JSON, a table on the run's summary page and one `::error` annotation per broken route, so the route is named on the run. **The first full run on a clean tree was NOT green**: `/signup` (bounced for a signed-in visitor, the mirror of `/login`), `/onboarding/checklist` and `/team/work-allocation` (redirect stubs) are deliberate and `EXPECTED_LANDINGS` predated them, so they are pinned with their reasons; a nightly that is red from day one for a false alarm is the check nobody reads. **A new redirect stub now turns the nightly red until it is added there, which is the intent.** **It has since run on GitHub** (8 October 2026): the two scheduled nights of 6 and 7 October were red only because 155 baseline entries in `axe-baseline.json` no longer fired (icon-only links that had been fixed; the ratchet fails a baselined finding that stops firing, by design), #704 deleted them, and a by-hand dispatch on `main` then finished green in 6 min 26 s for the build and the walk together.

## From CLAUDE.md section: Migrations

- **EACH MIGRATION IS ONE TRANSACTION, AND A REMEMBERED FAILURE KEEPS THE PIPELINE RED** (ops-16). `apply_migrations` ran psql with `ON_ERROR_STOP` but not `--single-transaction`, so a file that failed on its third statement had already committed the first two on the live database, and because a failure is remembered and never retried they stayed (its docstring records this for 055). Separately `RunReport.ok` was `not failed`, and a failure remembered from an earlier run lands in `skipped_failed_before`, which `ok` ignored: after one red run the NEXT push skipped the broken file, applied what else was pending and exited 0 with the change still unapplied. Each file now runs under `psql --single-transaction` with its `schema_migrations` row inside it, UNLESS a scan says that would be wrong: `strip_sql`/`transaction_plan` read the file as the server does (comments, string literals and `$$` bodies blanked first, because a grep for BEGIN finds every plpgsql function) and leave unwrapped a file with its own BEGIN/COMMIT (109 do), `CONCURRENTLY`, `VACUUM`, `ALTER TYPE ... ADD VALUE`, a `BEGIN ATOMIC` body, or a line `-- migration: no-transaction` (only in a NEW file: editing an applied one changes its checksum and re-runs it in production). The reason is reported per file (`not_atomic`, also in `--dry-run`). **THE TEN FAILURES THE REPOSITORY ALREADY TOLERATES ARE `BASELINE_FAILURES`, EQUAL TO THE HARNESS'S `EXPECTED_MIGRATION_FAILURES` AND MAY ONLY SHRINK**: a remembered failure of one does not turn the run red, and they keep the legacy partial-apply behaviour instead of being wrapped, because each commits what precedes its failure on a fresh database and every later migration and `*_pg.py` test was written against that schema. **A remembered failure outside that set keeps `ok` false**, with an error annotation to stderr (stdout is the JSON the harness parses); the run still continues past it, since stopping would hold every later migration hostage to one broken file. A transaction holds every lock until it ends, so a migration touching several hot tables now waits for all of them: keep it short. ⚠️ **If production's `schema_migration_failures` holds a row outside the ten, the first push after this merges is red until it is cleared** (`docs/deploy-migrations.md`); read the table once first. Not run: `tests/test_a_migration_is_atomic_pg.py` needs a Postgres this environment lacked, and the `migration apply` job is its first execution. A helper file in `tests/` must be declared in `test_a_file_in_tests_is_a_test_or_a_named_helper.py`'s HELPERS with its reason (`_fake_psql.py` was not, and only the full suite saw it).

- **THE SCHEMA-DRIFT CHECK HEALS ITSELF AND COVERS THE TABLES AND FUNCTIONS THE CODE CALLS** (ops-19). `core/schema_guard` computed its verdict once at boot, so a deploy that booted in the minutes before its migration landed answered 503 until the next restart; a boot that could not read the schema stayed 'checking' for the life of the process; and it knew only `ADD COLUMN IF NOT EXISTS`, so a migration that created a table or function and added no column produced no expectation. `start_drift_watch` re-asks every two minutes while the verdict is drifted or unread and ends at the first clean answer; a clean boot starts none, so it can only move a verdict towards healthy and never newly turn a healthy instance's `/health` into a 503 hours later, and 'not yet checked' is still never a 503. `check_schema_objects` compares the tables the code names in `.table('..')` and the functions in `.rpc('..')` with the live catalogue, read from the running source and not the migrations (462 migrations create things nothing calls; code naming a table production lacks IS the incident). Functions come from `get_public_schema_functions()` (**migration 475**: one jsonb row with a total counted apart so completeness is provable, `service_role` only, revoked from PUBLIC, anon and authenticated by name); a database without it is 'functions not checked', never 'every function missing'. **It REPORTS and does not yet GATE**: `schema_objects` on `/health` and a CRITICAL log, and `OBJECT_DRIFT_FAILS_HEALTH` is False because there is no production snapshot of functions and a 503 over something nobody could measure pulls the service. Flipping it is one constant, for a person who has read `schema_objects` on production and found it empty. ⚠️ **This migration was written as 474, and 474 was taken**: gst-06 (#674) landed `474_the_credit_ledger_...` on origin/main and in production first, and a branch cut before that merge cannot see it. Number a migration against `origin/main`, not against the branch you are standing on. **IT COMPARES DEFAULTS IN THE TWO DIRECTIONS THAT MATTER (POST-A-168, migration 561, 28-10-2026).** The check compared presence, type and nullability and never the default, so a default the migrations gave a column that production requires and does not default was invisible: code written from the migrations omits the column, the test database accepts the insert and production rejects it, the mirror of `form_26as_uploads.uploaded_by`. `schema_drift.diff` now reports `live_lacks_a_default_the_migrations_give` (NOT NULL in production, no default there, a default in the migrations) and `default_value_differs` (both give one and the values differ, after dropping casts and reading the two UUID functions as one), and `tests/test_schema_matches_production_pg.py` asserts both with the same in-flight excuse as its siblings. The first run found 39 differing defaults: 26 harmless, two that are not rejections (POST-A-356), and 11 that migration 561 settled (nine defaults production lacked, `tally_migration_jobs.is_dry_run` true and `form_26as_reconciliations.status` 'pending', made the production values). Without the migration the two new tests fail on exactly those columns. The excuse is by column NAME, as the other tests' is, so a column named like one a later migration mentions is excused for a release; the snapshot refresh (POST-A-351) is what removes the excuse.

- **A LOOKUP THAT MAY FIND NOTHING IS `.maybe_single()`, AND A `.single()` THAT SLIPS THROUGH ANYWAY ANSWERS 404 AND NOT 500** (POST-A-198, 17-10-2026). PostgREST's `.single()` RAISES when no row matches (406, code PGRST116, details "The result contains 0 rows"). Thirty-six lookups across the relationships, lifecycle, health and year-end-notes routers, the bank, banking and journal services and the income-tax, GST and Tally domain modules were written as `... .single().execute().data` followed by `if not row: raise 404`, and that line could never run: `core.exceptions._sqlstate` reads only five-character SQLSTATEs, so the eight-character PGRST116 fell through to the catch-all and a wrong or foreign id answered 500 "Internal server error (reference ...)" with a traceback in the log. They are `.maybe_single()` now (`core/supabase_client` restores the zero-row-returns-`data=None` contract at the library seam, so the line beneath finally runs). **A net for the next one**: `core.exceptions.is_absent_single_row` reads PGRST116 with "contains 0 rows" and `unhandled_failure` answers it 404 "That record was not found." from any other `.single()`; "contains 2 rows" (an inconsistency, one row was promised) and every other PostgREST code stay a 500. **The rule is `tests/test_a_lookup_that_may_find_nothing_does_not_use_single.py`**, read off the AST: a `.single()` call outside a `try` that has an `except` clause fails, a mention in a comment or docstring is not a call, and a call inside the handler itself is not protected. The lifecycle handlers ask a scope helper first, so for them the converted line is reached only when the row goes between that check and the read (a delete in another tab); that window is what it now handles. NOT DONE: 28 `.single()` calls remain (engagement letters, the year-end screens, the posting-account lookups), each inside an `except Exception` that does not re-raise, so they answer 404 for a wrong id but ALSO read a refused permission or a timeout as "absent"; that is the swallowed-exception work, POST-A-021, and was left alone because converting them changes what a database fault looks like to the caller.

EXCEPTION WHEN check_violation` block**, so they bind every new and changed row at once, and an old row that fails (one written between the read and the run) leaves the constraint NOT VALID with a NOTICE instead of failing the deploy (migration 479's pattern), still binding new rows. **The SQL list is a second copy of a Python vocabulary, which is what the posting-kernel rule exists to prevent, so it is pinned three ways:** `tests/test_the_chart_mapping_check_lists_what_the_classifier_reads.py` (mock suite, so the FIRST required check holds it: the migration's list equals `accepted_stored_spellings()`, and the served menu plus `also_accepted` equals it too), the real-Postgres test beside the migration (the accepted set read back from `pg_get_constraintdef` of a migration-built database equals the Python set, every readable spelling is accepted, a made-up, empty, padded or wrongly cased one is refused on INSERT and UPDATE), and `canonical_caption` itself, which strips: **a padded spelling is READ by Python and REFUSED by SQL, so every writer strips first** (the API models and the import screen do). **The import screen is part of the change, not an afterthought**: with the CHECK in place a CSV with a made-up caption would fail a whole batch of rows with a raw constraint message and no row number (and the screen's inserted-count arithmetic subtracts one error per batch). `GET /api/accounting/schedule-iii/captions` now also serves `also_accepted` (the older spellings and the heading, the picker never offers them), and `app/accounting/coa-import` builds its accepted set from the menu plus that list (`lib/accounting/coaImportMapping`), names the offending ROW and leaves it out of the import with the other row validations, and says the cell "could not be checked" when the vocabulary did not load, never silently passing it; an export of an older chart re-imports. **A journal UPDATE test must target a DRAFT**: a posted entry is refused earlier, by the immutability trigger, with a different error, and an assertion that expects the CHECK's name fails for a reason that has nothing to do with the CHECK (found when the first run's UPDATE case did exactly that). **Not done:** the document-store picker on the journal editor (the second half of A-163's text: attachments there are a typed LINK only, deliberately, and the `{name, document_id}` shape the domain already parses has no screen to produce it, which is a UI feature, not a constraint);
