## From CLAUDE.md section: Not built yet — known, deliberate, and not to be quietly started

**THERE ARE TWO TRACKERS AND BOTH LOCK THE PERIOD** (gst-27, practice_management-15,
frontend_ux-26). GST-14 made the `/gst` tracker (`compliance_calendar`) write
`public.filings`; the OTHER tracker, `compliance_records` — which `/deadlines`, a
client's Compliance tab and Practice → Compliance all show — moved an obligation to
"Filed" and wrote nothing else, so the two doors a CA actually uses were the two that
locked nothing. `compliance_record_service.update_record` is the ONE place an
obligation becomes Filed, so the filing is recorded THERE and `mark-filed`,
`transition` and `PATCH /compliance-records` all get it. For a GSTR-1 or GSTR-3B it
writes the `filings` row over the obligation's OWN period bounds (a QRMP quarter locks
all three months) **before** the status moves, so a failed write leaves the obligation
open for a retry rather than Filed-but-unlocked (`record_filing` is idempotent).
**The filed date is REQUIRED for those two and never defaulted** — the lock message
quotes it — and a refusal is asked BEFORE the first step of the four-step walk, so it
does not strand the obligation at Ready To File. A record cannot be CREATED already
Filed (a second way to Filed that locks nothing), and `gst_filing_record_service` now
holds the one map of which returns lock and the per-type reason for each that does not
(GSTR-9, TDS, ITR…), re-exported by the calendar router so the two doors cannot
disagree. The screens share `components/compliance/MarkFiledModal` and tell the CA what
the server did (`lib/compliance/filingOutcome`, which renders an ABSENT answer as
"could not confirm", never as "nothing was locked"). Nothing is backfilled: production
held one GSTR-3B obligation Filed without a lock, in a QA test firm. **THE WORKSPACE DOORS ASK FOR THE DATE TOO** (PRE-A-007, 08-10-2026): `record_filing` used to default a missing `filed_date` to today for a GSTR-1 or GSTR-3B, and the two firm-level mark-filed dialogs sent none, so a return filed on the portal on the 11th and recorded on the 14th was stamped the 14th, the date the period lock quotes and the s.37(3)/39(9)/16(4) window is measured from. `gst_filing_record_service.checked_filed_date` is the one rule (required, a real YYYY-MM-DD, not in the future, not before the period it declares ended, a QRMP quarter judged on the quarter's end), asked BEFORE the status moves by `routers/gst_workspace` (a refusal is that router's HTTP 200 `{success:false}` with the sentence) and by the calendar door (422), because `record_filing` sits in a swallow-and-log `try` and a refusal raised inside it would leave a return Filed with no `filings` row and so no lock. `markGSTR1Filed` / `markGSTR3BFiled` take a required `filedDate`; the two dialogs use `DateInput` with the `useDateProblems` gate, start empty and show the server's sentence. Other filing types keep today's behaviour. Not changed: the per-client GST tab's `MarkFiledDialog` still prefills its native date input with today (the guard covers that it sends `filed_date`), and `filing_history` shows `submitted_at`, the recording time, not the portal date.

## From the 14-10-2026 audit of the browser's direct writes

- **A GST RETURN IS APPROVED, REBUILT AND REOPENED THROUGH THE API, AND THE DATABASE ASKS WHO MAY APPROVE** (migration 491, ledger POST-A-223 and POST-A-224). Four defects of one family, found by an audit of every write the browser makes straight to the database. (1) `approveGSTR1` / `approveGSTR3B` set `status: "ca_approved"` and `ca_approved_by` on the return table themselves, with the approver supplied by the page. The route reserves approval to `gst:approve` (Manager and above); the table's policy asks `gst:compute` (Executive); a row policy cannot tell an approval from any other UPDATE, so an Executive approved a return, and the page sent the Supabase AUTH id for a column that is a foreign key to the INTERNAL user id. They now PATCH the status route like `markGSTR1Filed` did already, and take no approver from the caller. (2) `saveGSTR1Return` / `saveGSTR3BReturn`, reached on every Build or Compute click, upserted `draft` or `validated` over whatever the row held: a return the CA had filed on the portal came back as an unfiled draft with a CA Approve button, its ARN, filing date and approver still on the row and the `filings` row (the period lock) still in place. They refuse a submitted return in the server's own words and void an earlier approval (the server's recompute does the same). (3) The server's save of the ANNUAL return did the same to a filed GSTR-9, and the status routes asked the ROLE and not the PERSON (`can(role, ...)`), so a Partner's grid decision was ignored; a re-save, a recompute, a delete and a PATCH to `draft` of an approved or filed return all went through for anyone who could compute. `_approval_needed_to_change` now asks `can_user(person, "gst", "approve")` before any of them, and a zero-row UPDATE is no longer read as success. (4) Migration 491 is the backstop for a request that is not the screen's: RESTRICTIVE policies on both tables so that a return currently `ca_approved` or `submitted` changes, and a return is given either status, only for someone for whom `my_permission('gst', 'approve', 'Manager')` holds, and a filed return is deleted by nobody signed in.
  - **THE GUARD THAT MISSED IT WAS WRITTEN FOR A SPELLING.** `a-filed-gst-return-locks-its-period.test.ts` looked for `submitted` and filed dates, so an approval and a reset to `draft` walked past it. It now asserts the approval and the save by their shape (no PostgREST write in `approve*`, the status route with the CA's confirmation, the envelope checked, no approver parameter; the save reads the existing status before it writes, refuses a filed return and voids an approval) and has a rule that nothing in the browser sets an approval on either table. Eleven of its new tests fail against the old code.
  - **WHAT IS NOT DONE.** The browser still computes and writes the whole return row itself (about thirty columns); moving that persistence to the server door is the larger fix the audit named, and the API's save door does not yet accept the credit-ledger columns the screen writes. A Manager can still move a submitted return back to draft through the status route (the route's rule, not a row-policy question). A save into a locked financial year is not refused on the browser path (the server door does). The GSTR-9 save keys on financial year and not on registration, so a client with two registrations collides.
  - **THE SAME RULE REACHES MCA FILINGS (migration 493, POST-A-225) AND THE ITR CALENDAR TICK (POST-A-226).** The MCA screen wrote `status: "filed"`, the SRN and a date straight into `mca_filings` in three places (create, mark one, mark a batch), and the create path supplied TODAY as the date a filing was made, a date the software invented and presented as a fact about MCA21. The route requires Manager and above and the CA's confirmation; the table's policy asks Executive. All three go through `PATCH /api/mca-workspace/filings/{id}/status` now, the add modal creates the row not started and records it filed afterwards with an SRN and a date the CA typed (an Executive is told the row exists and was not marked filed), and the route asks the PERSON (`can_user`), refuses a zero-row UPDATE as a failure and refuses to reopen a filed filing without approval. Migration 493 is the backstop on `mca_filings` with the same shape as 491. The ITR screen's single and bulk "mark filed" wrote `filing_status: "filed"` into `compliance_calendar`; they use `api.compliance.markFiled` like the GST tracker, which cleans the date, audits and answers a refusal as `{ success: false }`. The tier is Executive at both ends, so that one is a bypass of checks and not a tier gap; the web guard's list of screens that still write a filing state is now EMPTY and `mca_filings` joined its table list.
  - **THE TAX AUDIT TRACKER IS THE LAST OF THE FAMILY, AND THE DATABASE ASKS WHO MAY CLOSE AN AUDIT** (migration 496, POST-A-226, 14-10-2026). The tracker wrote `tax_audits` straight from the browser, including `status = 'completed'` or `'filed'` with a UDIN, an acknowledgement number and a filing date, at the Executive tier (`income_tax:compute`, migration 261), while the matching ITR filing record is a Manager's and goes through the API. Recording an audit as completed or filed says the auditor has signed and the report is on the portal, so it is the same kind of statement as a filed return and now has the same tier. Of the two ways the ledger line offered (a status door through the API, or a check in the database) the second was taken: there is no tax-audit router at all, the screen already owns the whole record, and a door would have been a new router for one status. Three RESTRICTIVE policies ask `my_permission('income_tax', 'approve', 'Manager')` (so the per-person grid counts, as at the routes): a row may be created `completed` or `filed`, given either status, or changed while it holds either, only by someone who may approve; an Executive still creates and progresses an audit that is not started or in progress. The screen asks the same permission once the person is known (until then it is not narrowed, because a gate that waited would turn a slow identity call into a screen that never opens): a person who may not close an audit is not offered the two statuses, is told in words who can, and finds an audit already in either status read-only. A policy that refuses an UPDATE finds no row and raises no error, so the update asks for the ids it reached and reports none as "not changed", and a database refusal of the new row (42501) is worded, not quoted.
  - **AN INDEPENDENT REVIEW OF THE DIFF FOUND THREE GAPS IN THE SCREEN, ALL FIXED HERE.** (1) The "record already exists" auto-switch copied the found audit's status, UDIN, acknowledgement number and dates into the form and never took them back out: change the client or year to a pair with no record and an approver saved a new audit "completed" under the previous client's UDIN, while a person who may not close audits saw "Not started" in a box that still held "completed" and was refused for it. The copied fields are now cleared when the pair no longer has a record. (2) While the lookup for a changed pair was in flight the old record was still the save target, so an update keyed on the old row's id carried the new pair in its payload; a found record now counts only while the form still names its client and year. (3) The zero-row sentence always blamed approval, which is wrong for a Reviewer (migration 261 refuses them every write); it now names both causes. `scripts/the-tax-audit-screen-asks-who-may-close-an-audit.test.ts` holds the screen and a rule that no other file writes the table; the real-database file runs every actor, the grid both ways, idempotency and the migration's own rollback re-opening the hole. The same review found no other writer or reader of the table anywhere (Form 3CD reads two columns; nothing depends on the status).
  - **NOT DONE.** Delete still asks migration 261's ROLE tier (Manager and above) and not the grid, so an Executive the Partner grants `income_tax:approve` can record and reopen an audit but cannot delete one (the broader role-versus-grid asymmetry of POST-A-219's remainder). The UDIN and acknowledgement number are not checked for shape. `tax_audit_checklists.status = 'finalised'` (the Form 3CD clauses) is the same kind of statement and was not covered by 496; the next bullet closes it. `complete_filing` on the MCA route still defaults the filing date to today when the caller sends none; the browser now always sends one. The MCA create route accepts only eight form types and the screen offers more, so creation stays a browser insert.
  - **THE FORM 3CD CHECKLIST'S `finalised` IS AN APPROVER'S ACT, AND ITS TABLE IS THE SERVER'S ALONE** (migration 500, POST-A-233, 17-10-2026). `PUT /api/income-tax/form-3cd` asked `income_tax:write` (Executive: the fieldwork tier, by the comment in `core/permissions.py`) and accepted the status `finalised`; the table (`tax_audit_checklists`, migration 014) had the firm rule, the assignment rule of 084 (read from production on 17-10-2026) and every privilege granted to signed-in users by migration 041. So a Partner, or a member assigned to the client, could write the status and the clauses straight over the database past the route; a member not assigned to the client could neither read nor write. Nothing in `apps/web` names the table and nothing reads the status for a figure, so no number moved; the statement at stake is that someone who may approve has signed the checklist off, the same kind of statement as 496's completed audit and 493's filed filing. Two locks, as in the others. The route and `form_3cd_service.save_manual_clauses` ask the PERSON (`can_user(income_tax, approve)`): giving the checklist `finalised`, or changing one that already has it to any status or any clause, needs approval, and the service's `may_approve` DEFAULTS TO FALSE so a caller that forgets to ask is refused. A non-approver's write is ONE statement, `UPDATE ... WHERE status <> 'finalised'`, because the service reads the row and writes it in two requests and an approver can finalise it between them. **A SAVE THAT SENDS NO STATUS LEAVES THE STATUS ALONE** (the request's `status` is optional now; a new checklist starts as `draft`): the screen used to send `draft` on every save, so a Manager saving one clause silently reopened a finalised checklist, and it now sends no status. No screen can finalise yet; this is the API's rule ready for the one that will. Migration 500 revokes every privilege on the table from `authenticated`, `anon` and PUBLIC (reads too: nothing reads it, so they were privilege nobody used), leaves `service_role` and the row policies alone as the second lock, and ends with a check of the EFFECTIVE privilege that fails the migration if any is left. Unlike 496 this is a REVOKE and not a row policy, because there is no screen to preserve: a row policy cannot see a transition and a privilege can refuse the whole door. `test_500_..._pg.py` proves the privilege (every signed-in role, a Manager inside the assignment, the platform's TRUNCATE and `anon` grants and a PUBLIC or column grant removed, the migration failing when another grantor's grant cannot be revoked, idempotency, the rollback re-opening the hole); `test_a_form_3cd_checklist_is_finalised_only_by_an_approver.py` proves the route and the service (the unit tests that assert the refusals fail against the old code) and holds the premise that the browser never names the table, by the parser and by a plain scan of every source file. NOT DONE: a Manager can still reopen a finalised checklist (the rule is who, not which transition); the route's no-database branch only echoes the request, so the half of the rule that needs a stored row is enforced only where one exists.

## From the 19-10-2026 browser walk of the seeded firm

- **A COMPLIANCE OBLIGATION IS OVERDUE BY ITS DATE, BECAUSE NOTHING WRITES THE WORD, AND ONE FUNCTION SAYS SO FOR EVERY READER** (found by opening the seeded firm's Deadlines and Dashboard side by side). `compliance_records.status` is the stored workflow state and "Overdue" in it is a transition somebody makes by hand (`compliance_record_service.VALID_TRANSITIONS`): no job, trigger or route sets it when a due date passes. The Deadlines screen knew that and derived it from the date (`apps/web/lib/compliance/overdue.ts`), so it counted 220 overdue obligations on the seeded firm; readers in seven backend modules asked for the stored word, so on the same firm the executive dashboard's `compliance_failures` was 0, the client health score deducted nothing for any filing however late, the risk engine and the insight generator raised nothing, the firm summary and the client workspace said 0 overdue, the memory profile counted no missed deadline, and the assistant was told "OVERDUE COMPLIANCE FILINGS: 0". Two screens of one firm answered with different numbers. `domain/practice/compliance_overdue.py` is the rule and every reader asks it: an obligation is overdue when it is not settled and either somebody moved it to "Overdue" by hand or its due date is strictly before the CA's day (due today is not late until the day is out; a missing date is never late; "today" is `ist_today()`, read once per answer and handed in, as a `date`: a datetime is read as its day, because "2026-10-20" sorts before "2026-10-20T10:00" and would call an obligation due today late). **Settled is "Filed" and "Completed"**: the older readers compared a status only with "Filed" (or carried their own words: the compliance-risk engine behind the digest and the recommendations treated "not_applicable", which is not a status of this table, as settled and "Completed" as not), so a Completed obligation with a past date counted as late and as high risk, a Completed one due in three days was announced as a deadline this week, and a client with only Completed filings could not be deleted ("not yet filed"). The readers moved onto the rule are the dashboard, the health and risk scores, the risk engine, the insight generator, the assistant's prompts, the memory profile, the firm summary, the client workspace summary, the compliance-risk engine and the Practice → Compliance dashboard (whose tile, workload counts and queue now use it, and whose queue rows carry the server's `overdue` flag so the screen's Overdue filter and red due dates stop deciding from the stored status; the browser keeps the old date test only as the fallback for the redeploy window). A prepared "Ready To File" return that has missed its date is critical, as the health score already counted it (its risk was the lowest in the module). **The insight generator became a write amplifier the moment "overdue" could fire**, so it is idempotent: a press raises nothing the client already has open or acknowledged (a dismissed one is raised again if still true), identified by title AND the start of the description, because the GSTR-1 and the TDS return of one month share a period label and so a title, and "due in 4 day(s)" yesterday is the same warning as "due in 3 day(s)" today. The executive dashboard's cache version moved to 3 so the stored zeros are not served. `_overdue_compliance_records`, the assistant's helper that asked the repository for the stored word, had no caller and was deleted. **THE GUARDS ARE FOUR, EACH BECAUSE THE LAST ONE WAS NOT ENOUGH** (`tests/test_one_rule_says_a_compliance_obligation_is_overdue.py`): the readers are driven with the stored word and the date disagreeing (a hand-set Overdue with a date ahead, a Completed record in the past), against classes of different size (late 2, settled-and-past 4, open 1) and a late row that belongs to another firm; the clock is frozen at 31 March 2026 and every question put to the rule is recorded, so a reader that hands it yesterday (which is what the UTC date is for five and a half hours of every night), a datetime or a day it worked out itself fails, which fixtures days from the boundary cannot see; a scan of the backend fails any comparison, `status=` keyword or PostgREST filter that hands a status the word in any case, and any use of `STORED_OVERDUE` outside the rule (the entities with their own "overdue" are named by function, not exempted by file, and an entry that stops matching fails); and an inventory of every literal "Overdue" in the backend by file, spelling-independent, so a new one in any role fails until somebody has looked at it. The inventory cannot see a word built from pieces, a lowercase one, or SQL. On the real stack the seeded firm's executive dashboard now says 220 late filings (the Deadlines screen's number) where it said 0, the firm summary 220, and the client with 31 late obligations scores 0 and critical, where those filings had cost it nothing. Deliberately NOT done: (1) the dashboard's firm health ring and `healthy_clients` read `clients.health_score`, a column that defaults to 100 (migration 003) and that nothing writes, so they said 100 and every client healthy; that was fixed in the batch after this one and is the entry "A CLIENT'S HEALTH IS THE HEALTH ENGINE'S STORED SCORE, AND A CLIENT WITH NONE IS NOT YET SCORED, NEVER HEALTHY" in `docs/design-record/ai.md`; (2) the firm-level /gst and /income-tax trackers read `compliance_calendar`, a different and unpopulated table (POST-A-208, whose text said Deadlines read it and now says what each screen reads); (3) readers that already derive lateness from the date and so agree with the rule except for a hand-set "Overdue" with a date ahead or none (the health router's three `.lt("due_date", today)` filters, the calendar's overdue bucket, the escalation tiers) and five screens that write `due_date < today` themselves, and the assistant's `firm_summary.get("filed")` that has no such key (POST-A-280 is open; the assistant's key was fixed by POST-A-281, see the last entry of `ai.md`); (4) no job writes "Overdue" onto a record, on purpose: a stored second copy of a fact a date decides goes stale the next day and needs a sweep to keep true; (5) cached assistant summaries live one to six hours and stored memory profiles are recomputed only when the memory job runs, so both keep the old zero until then; (6) the seeded books are FY 2025-26, so every seeded obligation is overdue on the day this is read, which is the demo's data and was not changed.

- **AN MCA FILING RECORDED AS FILED CLOSES ITS CALENDAR OBLIGATION, AND THE OBLIGATION IS THE CLIENT'S WHILE THE FILINGS ARE THE COMPANIES'** (POST-A-267, the MCA door; the fourth of the workspace closers after the GST, ITR and TDS ones, found by reading the router and finding that it never mentioned `compliance_records`). `PATCH /api/mca-workspace/filings/{id}/status` to filed (and `PUT .../complete`, which calls it) recorded the filing and left the `MCA_AOC4` / `MCA_MGT7` obligation on the compliance calendar Not Started, so a company whose AOC-4 was filed on MCA21 in October read Filed in the workspace and Overdue on Deadlines, the Compliance tab and the firm dashboard. `services/mca_filing_closes_obligation.close_for_filed_filing` now closes it THROUGH `services/obligation_closure.mark_filed_and_answer`, the one place that holds the failure and race semantics, with the date and the SRN the CA stated, and the response gains `compliance_obligation: {state, closed, obligation_id, message}` the way the other three do. The obligation is the one of the filing's own form (`OBLIGATION_FOR_FORM`: AOC-4 to `MCA_AOC4`, MGT-7 to `MCA_MGT7`, ADT-1 to `MCA_ADT1`) and the filing's own financial year, matched on the year's first AND last day and never inferred from the due date, which moves with the AGM. The year is the filing's `financial_year`, or only when that is blank the `period` ("FY 2025-26") that the firm-level MCA screen writes instead (it inserts the row itself and sets no year, which the first version of this change did not know: it could never have closed a filing made there, and an independent review found it); a `financial_year` that is filled in but is not a year is not rescued by the period (`filing_year`). An event form (DIR-12, INC-22, SH-7, CHG-1, CHG-4) has no obligation on the calendar, so the router does not ask and the response carries no block; `MCA_ADT1` is named in `RETURN_OBLIGATION_TYPES` but nothing generates one, so an ADT-1 answers `not_on_the_calendar` until something does. An MGT-7A is matched to NO obligation, on purpose, and says so (`not_matched_to_an_obligation`): whether it discharges the `MCA_MGT7` the calendar generates for every company is a reading of the Companies Act and its Rules that has not been confirmed from the text (POST-C-209), so it is assumed in neither direction. A filing with no stated date closes nothing and says so, because `mark_filed` would write today's date for a non-GST return and the date it was filed on MCA21 is a fact this product does not hold (`PUT .../complete` is the one route that stamps today on the FILING itself when none is given, so the calendar then carries the date the filing carries). THE OBLIGATION IS THE CLIENT'S AND THE FILINGS ARE THE COMPANIES': `mca_companies` allows several per client (its unique key is the pair client and CIN), so with more than one ACTIVE company the obligation stays open until each of them has the form recorded as filed for the year (`waiting_for_other_companies`, naming the ones still to file), and a filing that names no company, or one that is not the client's, cannot be placed among several (`which_company_is_unknown`). The same shape as the GST closer's several registrations. One company or none closes on its own filing. A filing names its company by `company_id` or, failing that, by the CIN it carries (`company_cin`, which the firm-level screen writes and the client tab and the API do not): `company_of` matches it, case and spaces aside, to exactly one of the client's companies. No screen offers a company choice on a new filing, so with several companies a filing made on the client tab is declined until the CA marks the obligation from Compliance (POST-A-291). It never fails the recording (the filing IS recorded; whatever stops the obligation closing is said in the answer and reported), does not touch an obligation already Filed or Completed, and does not act for a caller without `compliance:write`, which is asked per person and is a different permission from the `mca:approve` that got the request this far. The client's filings tab shows the server's sentence in the same note the ITR screen uses, and the firm-level MCA page, which records a filing as filed in three places (add, mark one, mark a batch), puts it in the success message of the one toast it raises (the toaster holds ONE toast, so a second raised in the same handler replaces the first and the sentence is gone before anyone can read it, which the first version did in two of the three), the batch naming the filing each sentence is about, all through `lib/compliance/obligationNote` and deciding nothing. `tests/test_an_mca_filing_is_recorded_filed_and_closes_its_obligation.py` pins the mapping to what the calendar generates (a new MCA obligation fails it until it says which form closes it), and `apps/web/scripts/an-mca-filing-recorded-filed-says-whether-its-obligation-closed.test.ts` the screens. Deliberately NOT done: moving a filing back out of Filed does not reopen its obligation (the same as the other three; a closed obligation can only go on to Completed, and the reopening path is on POST-A-267); the route used to take the filing date as free text, so a date before the year ended or in the future was stored on the filing and refused by the calendar (fixed by the last entry of this file, POST-A-290); no obligation is generated for an ADT-1; a legacy filing with no client is answered that it names none, with nothing read for it.

- **AN MCA FILING'S DATE IS JUDGED BEFORE IT IS STORED, BY THE RULE THE ITR ACKNOWLEDGEMENT USES** (POST-A-290, found by the independent review of the MCA closer). `UpdateFilingStatusRequest.filing_date` was free text. A malformed value reached the DATE column and came back as "Unable to complete MCA operation" with no reason; a date in the future, or before the financial year an AOC-4 or MGT-7 declares had ended, was stored on the filing while `mark_filed` refused it, so the filing said it was filed on a day the calendar would not accept and the obligation was left open with the reason in the answer. The ITR acknowledgement had refused all three before storing anything. `PATCH /api/mca-workspace/filings/{id}/status` (and `PUT .../complete`, which stamps today when none is given) now judges the date first: `clean_filed_date` (a real date, not in the future on the Indian day, the GST status door's rule) and, for the two forms that describe a finished year, `compliance_record_service.year_end_not_yet_reached_on`, which is also what the ITR acknowledgement asks (it normalises the year label first, because `fy_bounds` reads four characters and ignores the rest, so "2025-99" would be judged as 2025-26).
