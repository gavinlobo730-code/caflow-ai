## From CLAUDE.md section: Where the design is written down

- **MIGRATION 481 IS THE SCHEMA FOR BOTH WORKFLOW HALVES, AND NOTHING READS IT YET** (POST-A-200, POST-A-204, 9-10-2026). `workflow_templates.archived_at` and `starter_key` (a plain `UNIQUE (firm_id, starter_key)`, deliberately not partial so `INSERT ... ON CONFLICT DO NOTHING` can arbitrate it; archiving a starter keeps its key); `workflow_instances` UNIQUE `(firm_id, template_id, idempotency_key)` WHERE the key is set AND status is not `failed` or `cancelled`, so a failed or cancelled run releases its key and an explicit retry is possible while a completed run keeps it, and the code reads SQLSTATE 23505 as "already started" (the partial index cannot be an `ON CONFLICT` arbiter through PostgREST); `tasks.workflow_instance_id` (`ON DELETE SET NULL`) and `workflow_step_ref` (text, not a foreign key, because an edit deletes and re-inserts steps with new ids), unique per `(firm_id, run, step)` while both are set, soft-deleted tasks included. It is additive and idempotent, rewrites no row, and REFUSES (naming the count) where live duplicate keys already exist. Production held no workflow template, run or schedule on 9 Oct 2026. **Code that names these columns must merge after 481 has applied**: `core/schema_guard` would report drift if an image that selects them booted first. Browser-writable `tasks` means a member could set the two task columns in their own firm; the engine must check a task's source and that a linked run belongs to the caller's firm.

- **A SAVED WORKFLOW RUNS EVERY STEP IT WAS SAVED WITH, AND A PERSON WHO PRESSES RUN RUNS THAT WORKFLOW** (POST-A-204, first slice, 9-10-2026). `domain/workflow/step_links.prepare` gives each step an id and links it to the next by list order at SAVE; a template with a branch or condition is stored unlinked (it ends after its first step, which the module says) and a link naming a step outside the save is removed. `workflow_repository._insert_steps` stores the steps in ONE statement and `_replace_steps` inserts before it deletes. `engine.start_manually` starts the ONE template named (a paused one too: the owner is asked to confirm), where the route used to start every template with the same trigger type. `check_idempotency` ignores failed and cancelled runs, matching migration 481's index, and a 23505 on creating a run is read as "already started". A run waiting on an approval is AT that step with its context stored; `resume_after_approval` reads the paused step from the action log and shares `_run_from`, so an approval as the last step completes. Deleting a template that has runs, and editing its steps while a run is in flight, answer 409. Not done: branch targets through the API, validating action types at save, role checks on an approval answer, audit rows and the other triggers.

- **THE TEAM SCREEN SAYS WHAT A BLOCK REACHES, AND A GUARD KEEPS THE SENTENCE TRUE** (POST-A-005, first slice, 9-10-2026). A per-person block is enforced by rbac() on every staff route (all but /api/identity/permissions and /api/security/mfa-policy) and by the write policies of eleven public tables (415, 470, 478); no public table's SELECT or ALL policy asks my_permission() EXCEPT the three payroll tables since migration 485 (attendance, leave and the declarations follow their employee), so a screen reading documents or bank accounts straight over PostgREST is not stopped by it; payroll is, and the notice says both. DENIAL_REACH_NOTICE (services/user_permission_service) is served as `notice` on the permission vocabulary and rendered through lib/team/denialNotice; a real-Postgres guard (pg_policies plus pg_proc fixed point, plus three end-to-end probes) fails the day a table read asks the grid, and its message names the notice, so the sentence is rewritten in the same commit. Verified against production on 9-10-2026 (read-only): the only SELECT policy that asks the grid is the storage policy for stored year-end export files, which is why the notice names it as the one read the grid reaches. Not done: the read policies for documents and bank (payroll was done by migration 485), each of which needs a decision first; see POST-A-005.

- **A STAFF INVITATION IS SENT BY THE SERVER, CAN BE SENT AGAIN, AND ITS LINK SIGNS THE INVITEE IN BY ITSELF** (POST-A-445, 16-11-2026). Invite Member created the member's row with a single-use token and a seven-day expiry and handed the token BACK to the Partner's browser, which asked Supabase to mail an ordinary sign-in link back to `/join?token=...`: the mail named neither the practice nor the Partner, it lasted only as long as Supabase keeps a one-time code, and nothing could send it again (the owner, inviting himself on the live site, 15-11-2026). `services/staff_invite_service` issues the token and mails it (`email_service.send_firm_invite`: the practice's name as the sender, the inviting Partner as Reply-To, the expiry in IST, every typed value escaped), and the create answer carries `member_state` and `invite_mail` ({sent, problem}, the mail service's answer). `POST /api/identity/users/{id}/resend-invite` (Partner) writes a fresh token and expiry over the old ones, so the earlier link stops working, and puts the old ones back when the new mail does not go (`kept_previous`), but only an earlier invitation whose link still worked (live and hashed) and only while the row still holds the token this resend wrote (`user_repo.restore_invitation`, a compare-and-set, so a withdraw, an acceptance or another resend that landed while the mail was on its way is never undone); it refuses in words a member who joined and a withdrawn invitation (Activate first). The join page reads only the token from the URL. Signed out it WAITS FOR A PRESS (a mail scanner that runs a link's scripts would otherwise use the invitation up), then asks `POST /api/identity/accept-invite/session` (public, rate-limited, on the unguarded invite router beside accept-invite) for a sign-in for the invitation's OWN address, redeems it with `verifyOtp` and accepts; a browser signed in as somebody else is told both addresses (the invited one is asked with `open_sign_in: false`, so merely looking creates nothing at Supabase) and signed out only from the button the person presses, and the sign-in is opened only after the sign-out. **THE TOKEN WAS A SIGN-IN, SO IT IS KEPT AS ONE** (the independent review of the first version found it): `users.invite_token` holds `sha256:<hex>` (`domain/firm/invite_token`; a value issued before the change keeps its plain form and can still be accepted by its own signed-in address, and opens no sign-in), the repository returns no row with the token or its hash except through `find_by_invite_token` (every other read and write gives `invite_outstanding` instead, which is all `member_state` needs; the team list, a role change, an activation and a forced sign-out each used to echo it, so a Manager could have joined as a pending Partner), the sign-in opens only for a live invitation the server mailed and NEVER for an address that already has a sign-in (409 in words: sign in as usual, then open the link; `services/sign_in_link.mint` retries as a magic link only for the employee portal, whose token was always hashed and never returned), and accept-invite refuses a sign-in that already belongs to a practice (`user_repo.find_linked_member`), because `core/auth` reads that link with `maybe_single` and a second row would lock its owner out of both practices. After joining, the page reads the membership again before the dashboard, or the app would send the new member to create a practice. After a withdraw or an activate the Team list is read again, because a local patch kept a withdrawn invitation showing Invited. Not done: whether Supabase gives an `invite` link to an address that already has an UNCONFIRMED sign-in (which would let somebody who pre-registered the address keep a way in) is unconfirmed and is POST-B-348; two resends at once each send a mail and the later token wins; a resend racing an acceptance can write a token onto a row that has just joined, which then matches nothing because the lookup asks for no sign-in.

### A PRACTICE STATES HOW LONG ONE FILING OF EACH KIND TAKES, AND THE ONE CAPACITY MODEL COUNTS IT FOR THE FILINGS NOBODY WORKS AS A TASK

POST-A-212, migration 671. Migration 452 gave a task its own whole-minute estimate and said in terms that an obligation not worked as a task has none, "a per-filing-type figure would be one the firm records (a table and a screen of its own), not one this migration can invent". This is that table and screen. `compliance_effort_estimates` holds, per firm and per obligation type (the calendar's own `compliance_type`), whole minutes above zero for ONE filing, unique on the pair, readable by a signed-in session and written only by the API's privileged client (`PUT`/`DELETE /api/workload/obligation-estimates`, `workload` write, Manager and above, audited under the sign-in id). `services/capacity_risk_service` reads the firm's rows once per forecast and gives each open obligation of a stated kind that many hours; an obligation worked as a task is still folded into the task and counted once by the task's own estimate. There is no default, no seed and no backfill: a kind with no row is an unknown, counted beside the hours as an item without an estimate and never averaged or read as zero, and clearing a figure makes the kind unknown again. The only bound is a sanity one (a year of minutes), said to be that. No statutory figure is held, because effort is not a date, a rate or a threshold. The panel on Team Workload lists the stated kinds and the kinds the calendar holds that have none, and is shown a box to type in only to someone holding `workload` write.
