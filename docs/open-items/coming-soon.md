# Coming soon — everything the product tells a person is not there yet

**Opened 9 October 2026 (IST), `main` at `3d97a71c`.** This file is the register of every statement a person is shown (on a screen, in the marketing site, in a filing walk-through or an emailed sentence) that something is **planned, coming, not built, or not switched on**: where it appears, its exact words, what gates it, who has to act and which ledger item holds the work. It is not a second ledger: the work lives in the six section files beside it, and a row here only says what a person is told about that work. If this file and the code disagree about a wording, the code wins and the row is wrong.

**Highest id issued: COMING-031** (ids are never reused: a deleted row's number stays spent).

## How to read a row

One line per row, in a fixed shape the test `apps/api/tests/test_the_coming_soon_register_is_well_formed.py` parses:

`- **COMING-001** · `kind` · `status` · gate:token,token — **Title.** What it is. — _Where:_ `path`, `path` — _Says:_ «exact words» «exact words» — _Safe:_ yes | no (why) — _Owner:_ A | B | C — _Ledger:_ ID, ID | none — _Switch:_ NAME — _Flow:_ key — _Claims:_ claim-id — _Added:_ 2026-10-09`

`_Switch:_` is required on a `switch` row, `_Flow:_` on a `walkthrough` row and `_Claims:_` is only for a `marketing` row. «» quote the words as they appear in the file (no sentence in the product contains them, which is why they are used); a quote is one run of text from a single string or paragraph, and where a sentence is written in pieces the quote is the piece. Paths are from the repository root and have no line numbers, because line numbers drift with every merge and the quoted words do not.

| field | values |
|---|---|
| kind | `promise` (a feature the product says it does not have yet: the row leaves when it is built) · `switch` (an off-state an owner-held setting controls: the row stays for as long as the code can show the off-state, even after the owner switches the feature on) · `walkthrough` (one per filing walk-through in `services/filing_demo`) · `marketing` (an offer, a link or a service commitment on the public site) |
| status | `shown` (the words are in the tree now; the test fails if they are not) · `queued` (decided, the words are not in the tree yet; the change that adds them flips the row to `shown`) |
| gate | `engineering` · `owner-decision` · `external-registration` (a GSP, ERI, NIC or similar registration) · `external-account` (a vendor account, key or sender) · `counsel` · `staffing` · `statute-reading` (a person reads the primary text) · `human-act-on-portal` (no registration unlocks it: a person does it on the authority's portal) · `owner-attestation` (a fact only the owner can confirm against a dashboard) |
| owner | the ledger's three buckets: **A** Claude can do it alone, **B** the owner decides and Claude builds, **C** only the owner or someone outside this container |
| ledger | the open-items ids whose work removes or changes the row (each must exist: closing one forces a look at the row), or `none` where no ledger line exists yet (a frozen list in the test, and the first thing to fix) |
| switch | environment variable names (checked against `render.yaml` and the API source) or `dashboard:Name` for a setting outside the repository. Whether a switch is on in production is not readable from the code: never write "currently off" in a row |

## The three house words

1. **"Coming soon"** is for an ordinary product feature that is decided and not yet built or switched on (online payment, say).
2. Anything about **filing, a registration or regulatory standing** says **"planned"** and names what gates it. It never says it is in motion: the list of words a filing sentence may not use is `domain.filing_posture.FORBIDDEN_REGISTRATION_CLAIMS` (decision D17: no registration has been sought yet), and the test applies it to every row about filing.
3. Something an **owner-held switch** gates says **"not switched on"** and names the switch.

The words follow what the thing IS, and the kind follows what controls it: online payment is an ordinary feature, so its label says "coming soon", and its row is a `switch` row because a provider key the owner holds decides whether the label is shown.

Nothing is ever sent to a client's customers automatically (decision D27): a "coming soon" label never means a scheduled send.

## What is not here, and why

Per-client and per-employee settings a Partner flips ("switched off for this client", "Not enabled" on a portal badge) are not owner-held switches. Operational errors (a missing storage bucket, a database that cannot be reached) are faults, not promises. Permanent decisions and named computation limits ("no FVU file is produced", "not modelled") say what the product does not do and does not promise to. Empty states ("No invoices yet") promise nothing. The two `.docx` master guides under `docs/` are internal and stale. Sentences from routes that answer 501 (a mock-mode answer) or 410 (no screen calls that route) are not here either.

## What the test checks, and what it does not

It checks the register is **true**: every row is well formed and has a unique id, the high-water line is not below the highest id, every ledger id exists, every path exists, the words of a `shown` row are still in its files, every switch name exists in `render.yaml` or the API source, every flow key and marketing claim id exists, and a row about filing uses none of the forbidden words (and says "planned" where a registration gates it). It does **not** yet find a promise that has no row: nothing scans the code for new "not yet", "planned", "coming soon" or "switched off" wording, so a statement added without a row passes today. That scan is a separate, later change; until it exists, a person adding such wording adds the row in the same commit.

## When a feature ships, a wording changes or a row is wrong

The commit that builds the feature, rewords the sentence or switches it on edits its row **in that commit**: a `promise` row is deleted, a `queued` row becomes `shown`, a `switch` row stays. A deleted row's id is not reused. Close the ledger item as usual (delete its line, rerun `python3 scripts/open_items_counts.py`); if a row still cites it, the test names the row.
